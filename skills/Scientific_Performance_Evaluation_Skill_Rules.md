# Scientific Performance Evaluation Skill

## 0. Purpose

This Skill operates after knowledge alignment and execution orchestration. It evaluates candidate solutions, model behavior, and run results produced by the execution layer. Its core purpose is not merely to generate charts or produce a single ranking, but to organize dispersed run logs, model outputs, domain calculations, public benchmarks, and expert judgments into decision-ready evidence that an interdisciplinary team can inspect jointly, and to formulate adjustment plans that can be fed back to the execution-orchestration stage.

This Skill primarily performs the following tasks:

1. Identify the current execution round, candidate objects, active metrics, tool interfaces, and result coverage;
2. When experts have not provided explicit analysis requirements, infer the scientific questions that different expert roles are likely to care about based on task semantics, upstream knowledge, run results, and retrievable evidence;
3. Convert inferred concerns or expert requests into scientific analysis and visualization plans with explicit evidence, boundaries, and priorities;
4. Register computational tools, analysis environments, rules, analysis requests, and visualization protocols provided by experts from different domains, and revise existing plans accordingly;
5. Invoke domain tools and, according to the analysis plan, write data-processing, statistical-analysis, and plotting scripts to generate reproducible tables and visualization figures;
6. Produce a computer-expert view, separate views for each domain expert, and a cross-domain joint view;
7. Compare results with baselines, historical rounds, or published work under conditionally consistent settings;
8. Diagnose performance bottlenecks, uncertainty, failure modes, and data gaps based on figures, performance records, and external evidence;
9. Record separately the adjustment recommendations generated by this Skill from figures and performance records and the adjustment proposals subsequently provided by experts, then synthesize them into a traceable, reviewable, and reversible adjustment plan mapped to execution parameters, models, datasets, metrics, constraints, or additional computation tasks.

This Skill is not restricted to a specific discipline, model, or software package. Domain tools may include scientific-computing software, experimental-data-processing tools, statistical packages, machine-learning frameworks, databases, rule checkers, or expert-provided custom scripts. Missing information must remain missing; commonsense assumptions or case-specific experience must not be used to fabricate run results.

This Skill defines the complete rules of the performance-evaluation stage. Expert-concern inference, evidence retrieval, analysis-plan design, code and script writing, tool invocation, figure generation, result diagnosis, and adjustment recommendations are all performed directly by this Skill in accordance with this document. Real expert opinions, upstream information, external evidence, and the inferences or diagnoses produced by this Skill must be attributed separately and must not be conflated.

## 1. Input Selection and Version Inheritance

### 1.1 Upstream files

Read files in the following priority order:

1. `execution_orchestration.yaml`: obtain active metrics, model interfaces, rewards, constraints, workflows, parameter controls, expected outputs, and authorization scope;
2. `execution_orchestration_report.md`: supplement execution logic, scientific explanations, run conditions, and expert views;
3. `execution_review_queue.yaml`: identify unresolved issues that may affect result interpretation;
4. `knowledge_alignment.yaml`: inherit metric definitions, units, conditions, evidence, proxy relationships, and expert status;
5. `knowledge_alignment_report.md`: supplement scientific background, mechanism explanations, and cross-domain semantics;
6. `expert_review_queue.yaml`: inherit unresolved knowledge issues that still affect performance judgments;
7. `execution_results/**`: read actual run outputs, candidate files, logs, checkpoints, predictions, computation results, experimental results, and resource records;
8. Expert analysis requests and adjustment requests: treat them as new inputs for the current round without overwriting existing records.

When filenames contain round or version identifiers, prioritize the latest `active`, `expert_approved`, `completed`, or explicitly specified version, while retaining its upstream and baseline versions for difference analysis. Scientific validity must not be inferred solely from file-modification time.

### 1.2 Input-state determination

First determine which state the current inputs represent:

- `planned_only`: only plans, metrics, and interfaces are available; no actual run results exist;
- `partially_executed`: some candidates, logs, or metrics exist, but coverage is incomplete;
- `completed_run`: complete and traceable run results exist;
- `multi_run_comparison`: multiple rounds, models, parameter sets, or data versions exist;
- `external_results_only`: only expert-provided results or external benchmarks are available;
- `invalid_or_untraceable`: results cannot be mapped to a run, candidate, tool, or version.

When no actual results are available, the Skill may only output evaluation readiness, proposed analysis protocols, visualization plans, and data gaps. It must not claim that the model has converged, that a candidate performs better, or that an adjustment has produced an effect.

```yaml
input_snapshot:
  snapshot_id: "INPUT-001"
  selected_versions: []
  inherited_versions: []
  execution_status: "planned_only|partially_executed|completed_run|multi_run_comparison|external_results_only|invalid_or_untraceable"
  available_artifacts: []
  missing_artifacts: []
  active_run_ids: []
  baseline_run_ids: []
  unresolved_upstream_issues: []
  evaluation_scope: []
```

## 2. Evaluation Subjects and Result Provenance

### 2.1 Evaluation subjects

Performance evaluation may operate at different levels of granularity:

- An entire workflow or a single run;
- A model, surrogate model, computational module, or evaluator;
- A dataset, data subset, or data split;
- A single candidate, candidate set, or Pareto set;
- A metric, metric group, or mechanism branch;
- Compute resources, failed tasks, and execution stability;
- Comparisons with historical rounds, baseline methods, or literature results.

```yaml
evaluation_subject:
  subject_id: "SUBJ-001"
  subject_type: "workflow|run|model|dataset|candidate|candidate_set|metric|branch|tool|environment"
  source_refs: []
  run_id: ""
  version: ""
  parent_subject_id: ""
  evaluation_questions: []
  status: "registered|ready|partial|evaluated|excluded"
```

### 2.2 Result records

All numeric values and conclusions must preserve their source type, conditions, tools, and uncertainty. Predicted, computed, measured, literature-reported, and secondarily derived values must not be conflated.

```yaml
performance_record:
  record_id: "PR-001"
  subject_id: ""
  metric_id: ""
  value: null
  unit: ""
  value_type: "measured|computed|predicted|derived|reported_literature|implementation_score"
  conditions: {}
  sample_size: null
  evaluator_id: ""
  environment_id: ""
  source_artifacts: []
  uncertainty: {type: "", value: null, interval: [], method: ""}
  data_quality: "high|medium|low|unknown"
  applicability_status: "in_domain|borderline|out_of_domain|unknown"
  missing_reason: ""
  validation_status: "unverified|checked|expert_reviewed|validated|rejected"
```

### 2.3 Provenance rules

- Every performance record must map to a candidate, run, model, or data version;
- Derived metrics computed from multiple fields must record the formula and all input records;
- Rewards, internal scores, or loss values in logs may only be interpreted as implementation metrics and must not be equated directly with terminal scientific performance;
- Results may be retained when units, conditions, sample granularity, or tool versions are missing, but their comparability must be downgraded;
- Any manual correction, outlier removal, unit conversion, normalization, or imputation must be recorded separately;
- Raw outputs must never be overwritten. Cleaned results, analysis tables, and visualization data must be stored separately.

## 3. Expert, Tool, and Environment Registration

This Skill supports one computer expert and multiple domain experts. Domain experts are distinguished by `domain_id`; opinions from different disciplines must not be merged into one generic “domain opinion.”

`expert_registry` registers only experts who have actually provided input, feedback, or authorization. “Potential expert concerns” inferred by this Skill must not be presented as real expert opinions. They must be recorded separately as `skill_inference` and remain subject to expert confirmation, revision, or rejection. Fields such as `target_perspective`, `audience`, or “expert view” indicate only the knowledge perspective and intended audience of the analysis; they do not imply that a corresponding expert entity exists or has expressed an opinion.

### 3.4 Tool-invocation rules

- Before activating a tool, confirm at minimum its inputs, outputs, units, version, environment, failure state, and result path;
- When an expert provides only a software name or paper, the tool remains `proposed` and must not be claimed as invoked;
- When a fixed execution entry point is provided but no parameter permission is granted, the tool may only run under its fixed configuration;
- This Skill may write adapters, batch-execution scripts, data-cleaning scripts, and plotting scripts, but must not modify the scientific settings of domain tools, original models, production scripts, or expert data without authorization;
- New scripts must be stored separately and must record dependencies, inputs, outputs, and versions;
- When a tool fails, the Skill must not use an unrelated tool to generate substitute values. It may downgrade the result to missing, request manual evaluation, or create a new computation request;
- When the same metric is produced by different tools, definitions and conditions must be checked before deciding whether the results can be combined.

- Papers, software documentation, and public webpages must have locatable sources, retrieval conditions, and applicability scope recorded;
- External evidence may support why a particular analysis or figure is needed, but it cannot substitute for actual results from the current task;
- When experts provide new tools, protocols, or interpretations, create new evidence records and revise the analysis plan without overwriting the original inference chain.

## 4. Inference of Expert Concerns and Analysis Requests

### 4.1 Inference of expert concerns

When no explicit expert information is available, or when experts provide only broad objectives, this Skill must proactively construct questions to be answered from different expert perspectives. The basis may include the scientific objective, active metrics, model type, data structure, run logs, domain mechanisms, common failure modes, and retrievable domain-evaluation practices.

```yaml
analysis_concern:
  concern_id: "CONCERN-001"
  target_perspective: "computer_expert|domain_expert|cross_domain_team|decision_maker"
  domain_id: ""
  question: ""
  concern_type: "model_behavior|scientific_performance|mechanism|data_quality|candidate_quality|resource|reproducibility|comparison|risk|decision"
  source_attribution: {}
  trigger_refs: []
  evidence_refs: []
  suggested_metric_ids: []
  suggested_analysis_methods: []
  suggested_visualization_types: []
  priority: "low|medium|high|critical"
  confidence: "high|medium|low|unknown"
  confirmation_status: "unconfirmed|expert_confirmed|expert_revised|expert_rejected|superseded"
  superseded_by: ""
```

Inference rules:

- Begin with upstream-defined metrics and actual outputs; do not introduce analyses unrelated to the task;
- The computer-expert perspective commonly concerns convergence, stability, generalization, data quality, resources, and reproducibility, but each specific question must be supported by the current model and available log fields;
- The domain-expert perspective commonly concerns mechanistic plausibility, terminal performance, metric trade-offs, condition dependence, domain benchmarks, and anomalous candidates, but general experience must not be written as the opinion of a real expert;
- When necessary, retrieve papers, software documentation, and public benchmarks to identify suitable analysis methods and scientific visualization forms for the domain;
- Every inferred concern must record its trigger, evidence, confidence, and pending-confirmation status;
- Subsequent expert input should preferentially revise the corresponding concern, while historical inferences are retained for version comparison.

### 4.2 Expert analysis requests

Experts may request additional computation, statistics, comparisons, figures, or interpretation. Such requests must be converted into executable analysis tasks rather than overwriting the original evaluation protocol.

Processing rules:

- When existing data support the request, create an analysis or visualization task;
- When the request requires new domain computation, bind the relevant tool, environment, budget, and authorization;
- When the request changes a metric definition, threshold, or scientific objective, do not modify it directly; generate an upstream adjustment recommendation or review item;
- Preserve conflicting requests from multiple experts separately and explain their implications in the joint view;
- When a request cannot be completed, state whether the reason is missing data, unavailable tools, inconsistent conditions, insufficient budget, or insufficient permissions.

### 5.3 General evaluation dimensions

Select from the following dimensions according to available data. Not every task must include all of them:

- **Scientific performance**: terminal metrics, proxy metrics, constraint pass rates, mechanism-related descriptors, and uncertainty;
- **Model behavior**: training/optimization convergence, stability, generalization, calibration, overfitting, mode collapse, or search stagnation;
- **Candidate-set quality**: validity, uniqueness, novelty, diversity, coverage, distribution shift, Pareto improvement, and failure types;
- **Data quality**: missingness, duplication, label noise, class/distribution imbalance, data leakage, split consistency, and applicability domain;
- **Execution performance**: runtime, throughput, success rate, resource usage, retries, tool failures, task queues, and cost;
- **Reproducibility**: random seeds, versions, environments, input snapshots, commands, logs, and output paths;
- **Comparative performance**: differences relative to baselines, historical rounds, ablation configurations, public data, or published work.

Do not generate unsupported dimensions merely for the sake of completeness.

## 6. Analysis Planning, Script Writing, and Visualization

This Skill first determines which scientific questions must be answered, which analytical methods should be used, which figures should be generated, and what the interpretation boundaries are. It then writes and executes the corresponding data-processing, statistical-analysis, and plotting scripts. Scientific questions, implementation methods, direct figure observations, scientific interpretations, and adjustment recommendations must be recorded separately so that code implementation is not mistaken for scientific opinion.

- When a tool is unavailable, an evidence-based fallback statistical or visualization method may be used, but domain-computation results must not be fabricated;
- Every revision must preserve the prior version, revision trigger, proposer, and supporting basis.

### 6.4 Audience-oriented views

**Computer-expert view** should prioritize the following questions:

- Has optimization or training converged, and is it stable?
- Do reward, loss, gradients, acceptance rate, or other key internal metrics exhibit stagnation, oscillation, or anomalies?
- Are training, validation, and test performance consistent?
- How do candidate validity, uniqueness, diversity, coverage, and failure rate change over time?
- Are resources, throughput, tool failures, or retries becoming bottlenecks?
- Are results reproducible across random seeds, model versions, or parameter configurations?

Optional figures include learning curves, rolling statistics, confidence intervals, calibration plots, error decompositions, resource curves, failure-type summaries, candidate coverage, and cross-round comparisons. They may only be generated when corresponding time-series or grouped data exist.

**Domain-expert views** must be generated separately by `domain_id` and should prioritize the following questions:

- Which metrics best reflect domain mechanisms and terminal performance?
- How do candidates behave in metric distributions, threshold pass rates, trade-offs, and structural or condition-dependent differences?
- Which results are mechanistically plausible, and which may reflect proxy bias or computational artifacts?
- How do the results compare with domain baselines, historical samples, or published work?
- Which candidates, subgroups, or anomalies warrant additional computation or experimental confirmation?

Optional figures include distributions, threshold pass rates, correlations and partial correlations, trade-off plots, Pareto plots, subgroup comparisons, error bars, structure–performance maps, condition-stratified plots, and candidate evidence cards. Figure types are determined by the scientific question and available data and must not be fixed to a single case.

**Cross-domain joint view** should preferentially use:

- Metric–candidate evidence matrices;
- Multi-objective Pareto fronts;
- Joint scorecards standardized by domain while retaining raw values;
- Decision tables presenting candidate advantages, risks, and evidence grades side by side;
- Relationship diagrams of metric conflicts, dependencies, and potential causal chains;
- Diagrams of data gaps, additional computation, and experimental-validation requirements.

Unless experts have approved a unified utility function, all domain metrics must not be compressed into one aggregate score by default.

## 7. Comparison with Baselines and Published Work

### 7.1 Comparison targets

Comparison targets may include:

- An unoptimized model or traditional workflow;
- A previous run, a different random seed, or an ablation configuration;
- Expert-provided known candidates, internal benchmarks, or experimental controls;
- Public datasets, standard test sets, or published work;
- Reference objects recomputed with the same domain tool under identical conditions.

### 7.2 Comparison rules

- Compare metric definitions, units, samples, data splits, experimental/computational conditions, model versions, and statistical conventions before comparing values;
- Only `directly_comparable` results may be used to calculate direct improvement ratios or statistical significance;
- `normalized_comparable` results must document the normalization, recomputation, or calibration procedure;
- `context_only` results may only provide order-of-magnitude or trend context and must not support claims of superiority over the literature;
- `not_comparable` results may be retained as background but must not enter rankings;
- Literature benchmark selection must record search scope and inclusion criteria to avoid cherry-picking favorable comparisons;
- When final performance depends on a domain tool, internal candidates and reference objects should preferably be recomputed under one tool and one protocol;
- Literature-reported and locally computed values must use different `value_type` values.

## 8. Cross-Domain Synthesis and Evidence Assessment

### 8.1 Figure observations and scientific interpretation

A figure is an evidence carrier and is not automatically equivalent to a conclusion. This Skill may perform initial pattern recognition and diagnosis on generated figures, while experts may confirm, revise, or provide alternative interpretations. Interpretations from different sources must be stored separately.

```yaml

  interpretation: ""

  decision_relevance: ""
  expert_status: "pending|confirmed|revised|disputed|rejected|not_required"
  supersedes_finding_id: ""
  status: "proposed|reviewed|active|superseded|rejected"
```

Rules:

- `observation` describes only patterns directly shown by a figure or statistic, whereas `interpretation` describes possible causes and scientific implications;
- Initial interpretations generated by this Skill must set `source_attribution.source_type` to `skill_analysis` and must not be written as expert conclusions;
- Experts may produce independent interpretations from the same figure; later opinions must not overwrite earlier judgments;
- Correlations shown in figures must not be stated as causal relationships without mechanistic evidence or controlled experiments;
- Adjustment plans should preferentially cite findings that have undergone statistical checks or expert review. Exploratory findings may still trigger additional computation but should not directly trigger broad model changes.

### 8.2 Synthesis principles

- Preserve each domain’s original metrics, units, conditions, and uncertainty;
- Normalize only when metric directions, scales, and applicability conditions are explicit;
- Hard-constraint failures take precedence over aggregate scores;
- Terminal performance takes precedence over proxy performance, but proxy evidence may be shown in parallel when terminal data are insufficient;
- When multi-objective conflicts are substantial, preserve Pareto sets, branches, or candidate clusters;
- Do not automatically treat missing values as poor performance, and do not retain candidates unconditionally because values are missing;
- Results with insufficient evidence, inconsistent conditions, or out-of-domain predictions receive lower confidence and trigger review;
- Cross-domain synthesis must explain who benefits, who is disadvantaged, and whether the trade-off is acceptable.

## 9. Performance Diagnosis and Adjustment Plans

### 9.1 Sources of diagnosis

Adjustment recommendations may originate from:

1. Reproducible observations in generated figures and statistical results;
2. Initial diagnosis by this Skill of run behavior, model behavior, domain performance, or mechanisms;
3. Interpretations of figures and results by domain experts or computer experts;
4. Cross-domain metric trade-offs and joint judgments;
5. Gaps identified through comparison with baselines or literature;
6. Data-quality, applicability-domain, or uncertainty issues;
7. Adjustment plans directly proposed by experts;
8. Unfinished computation, experiments, or validation requirements.

Every adjustment recommendation must cite specific `analysis_finding`, `cross_domain_finding`, `visualization_spec`, or `performance_record` objects. A statement such as “the model believes this may be better” is insufficient for a high-priority adjustment.

### 9.2 Adjustment targets

Adjustment plans may target:

- Execution-orchestration parameters: budget, step count, sampling strategy, search range, reward weights, soft constraints, stopping conditions, and similar settings;
- Models: model type, architecture, loss, hyperparameters, checkpoints, surrogate models, calibration, or uncertainty modules;
- Datasets: data cleaning, additional samples, label revision, resampling, data splits, augmentation, applicability-domain coverage, or experimental design;
- Metrics and protocols: new metrics, removal of redundant metrics, threshold calibration, measurement conditions, or comparison protocols;
- Domain tools: method replacement, additional high-accuracy computation, condition harmonization, or repair of failed interfaces;
- Workflows: additional screening layers, node reordering, parallel branches, human-review points, or rollback points;
- Knowledge alignment: return to knowledge alignment when metric meanings, mechanism branches, or expert consensus require reconfirmation.


## 11. Multi-Round Evaluation and Change Attribution

Performance evaluation may be repeated after multiple execution rounds. Each round must preserve its input snapshot, tool versions, analysis protocols, and outputs; previous rounds must not be overwritten.

Cross-round comparisons must distinguish at least:

- Parameter changes;
- Model or checkpoint changes;
- Dataset, split, or label changes;
- Metric, threshold, or reward changes;
- Tool, computational-method, or environment changes;
- Random-seed and sampling variation;
- Expert-rule or screening-condition changes.

When multiple factors change simultaneously, only a joint change may be reported; improvement must not be attributed to a single factor. Attribution requires an ablation, control, or controlled pilot run.

## 13. Checks, Degradation, and Stopping

### 13.1 Pre-execution checks

Confirm that:

- The current evaluation subject and run version are traceable;
- Actual results are distinguished from planned outputs;
- Real expert inputs, Skill-generated inferences, and external evidence are distinguished;
- Every analytical concern and analysis plan has a proposer, basis, confidence level, and confirmation status;
- Every active metric has a definition, unit, conditions, source, and evaluator;
- Tool and environment interfaces are registered and have passed a minimum test;
- Predictions, computations, experiments, literature reports, and implementation scores are distinguished;
- Comparison targets have explicit comparability assessments;
- Visualization questions, fields, transformations, and uncertainty displays are defined;
- Visualization plans, script-execution records, code, figure artifacts, and figure findings can be mapped to one another;
- Expert requests are mapped to data and tools;
- Adjustment recommendations have an originator, figure or finding basis, target, risk, validation plan, and rollback plan.

### 13.2 Degradation strategies

- Incomplete results: downgrade to readiness analysis and a data-gap inventory;
- Unavailable tools: retain the task and route it to manual review, a fallback tool, or an additional-computation request;
- Too few samples: report descriptive results only and avoid unstable statistical inference;
- Inconsistent conditions: stratify the presentation or mark the comparison as contextual;
- Missing uncertainty: state the limitation and do not fabricate error bars;
- Convergence cannot be computed: report only the run-behavior information that is available;
- No unified aggregate objective: retain multiple metrics and Pareto results rather than generating a total score.

### 13.3 Pause or stop conditions

Pause the relevant evaluation or adjustment output when:

- Results cannot be mapped to candidates, runs, models, or data versions;
- Metric units, definitions, conditions, or sample granularity contain critical conflicts;
- Domain-tool outputs cannot be mapped to metrics;
- Tools, scripts, environments, or versions are untraceable;
- Training/test data leakage exists or the evaluation set has been used for tuning;
- Literature or baselines are not comparable but an “improvement” calculation is requested;
- Predictions are out of domain and uncertainty is not handled;
- Experts have unresolved conflicts over critical terminal metrics or thresholds;
- Code or script execution attempts to modify unauthorized scientific settings, models, or raw data;
- An adjustment plan exceeds the authorization boundary of execution orchestration;
- Budget, resource, or stopping conditions have been reached;
- An expert pauses or rejects a critical object.

## 16. Behavioral Rules

- Inherit knowledge alignment and execution orchestration without redefining unapproved scientific objectives;
- Confirm whether actual results exist before determining evaluation depth;
- Support multiple domain experts, multiple tool environments, and multiple analytical views;
- When expert information is insufficient, proactively infer scientific concerns from different expert perspectives and, when necessary, retrieve papers, software documentation, or public benchmarks to design analyses and figures;
- Skill-generated inferences must be labeled `skill_inference`, while real expert opinions must record the corresponding expert ID; the two must not be mixed;
- The computer-expert perspective focuses on model behavior, engineering stability, data, and resources; domain-expert perspectives focus on mechanisms, performance, conditions, and domain benchmarks;
- This Skill is directly responsible for scientific-question inference, evidence retrieval, analysis planning, code and script writing, tool invocation, visualization generation, and initial diagnosis; no independent execution actor is introduced;
- This Skill does not replace the scientific computation logic of domain tools or the final judgment of experts;
- When experts provide new scientific tools or plotting protocols, update and version the analysis and visualization plans rather than silently replacing scripts;
- Maintain explicit links among metrics, results, tools, environments, candidates, runs, and figures;
- Proxy metrics, rewards, and internal scores must not be presented as terminal performance;
- Comparisons with published work require prior assessment of methodological and conditional comparability;
- Cross-domain synthesis preserves multiple metrics and Pareto structures by default and does not force a single aggregate score;
- Recommendations generated by this Skill and recommendations from experts must be recorded side by side; conflicts must not be hidden;
- Every finding and adjustment recommendation must state its proposer, source basis, referenced figures or records, and confidence status;
- Adjustment plans may involve execution parameters, models, datasets, metrics, tools, or workflows, but by default only recommendations and pilot plans are produced;
- Actual modifications must return to execution orchestration and follow its authorization, boundary, testing, versioning, and rollback requirements;
- Noncritical missing information does not block the workflow; critical conflicts enter the review queue;
- All analyses must be reproducible, traceable, pausable, revisable, and reversible;
- Final scientific judgment remains expert-led; this Skill expands computation, organizes evidence, and exposes uncertainty.
