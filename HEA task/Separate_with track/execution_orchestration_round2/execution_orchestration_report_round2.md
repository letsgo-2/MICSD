## 1. Scope and execution status

### Blocking implementation mismatch

Project order is `[Pd, Pt, Au, Cr, Ir, Ce, Cu, Nb]`; AL fixes `[Pd, Pt, Cu, Au, Ir, Ce, Nb, Cr]` in `costs.py:6`, `data.py`, and `providers.py:51-54`. A positional vector cannot be passed between these interfaces unchanged. In addition, both input loading and LLM output call `normalize_ratio`, which repairs sums rather than rejecting invalid records. **Do not run the current package on project data until order/basis mapping is explicit and validation preserves raw vectors while rejecting invalid inputs.** No code was changed in this task.

## 3. Revised metric ranking and thresholds

Ranking is based on decision priority, not on an unapproved scalar reward. For actual optimization, P_peak is the single primary objective as confirmed by the computer expert. Composition constraints are gates executed before candidate scoring. Other factors are displayed independently.

|---|---|---|---|---|

| Gate 2 | Nonnegativity and closure | Hard constraint; each `x_i >= 0`, `sum(x)=1` | Reject invalid raw values; do not silently normalize. ## 4. Proposed execution procedure for approval

No step below is executed by this task. Proposed run should remain blocked until steps 1-4 are confirmed.

1. **Confirm data basis and schema.** Inspect project data metadata, determine mass vs atomic/molar basis, units, element order, device protocol and whether `AL/data/*.csv` are demonstration data or project experiments. Create an immutable source copy; map by element name, never by position. Preserve raw vectors, reject nonfinite/negative/nonclosing data rather than silently normalize. Retain nominal, measured bulk and surface compositions separately.
2. **Approve metric policy.** Keep P_peak as sole primary objective. Decide whether normalized cost is reporting-only, a Pareto objective, or a budget constraint; define any element-specific ranges/support rule. Confirm novelty-distance and LLM disagreement are diagnostics. Defer stability until protocol and data are supplied. Do not use the code's target improvement assumptions or `performance_threshold=200` unless explicitly approved.
3. **Choose execution mode.** The existing AL simulation calls a live LLM and uses the GBR as a virtual oracle. It is not a real experimental closed loop. For an initial software-only simulation, explicitly approve API use, model/provider, maximum calls, spend cap, and separate output directory. For scientific evaluation, do not describe GBR outputs as measurements; specify how candidates receive measured device results and how the sample pool is updated.
4. **Resolve model/data interfaces before adaptation.** Update adapter/config to use the approved project order and basis, named columns, data provenance, units/conditions, split by composition/synthesis group, and explicit invalid-row reporting. Confirm whether a GBR artifact already exists and its provenance; never auto-train or overwrite without approval. Register all model versions, API model identifier, prompt/version, preprocessing, random seed, validation and domain limits.
5. **Preflight without running the model.** After approval, first permit only static schema/config review or explicitly authorized unit tests with mocked provider; do not run `run.py`, `train_oracle.py`, `check_environment.py`, or real API calls unless separately authorized. The package README's environment check reads environment and checks API variables; it is not needed for this proposal.
6. **Run a bounded pilot only after explicit authorization.** If approved, set an empty new output directory and conservative, approved iteration/pool/API-call limits. The README suggests one iteration, pool 2000, while config defaults imply 31 API calls/round (1 recipe plus 10×3 committee calls). Actual call accounting and provider retries must be confirmed. Existing `query_top_k=8` means eight GBR virtual evaluations per round, not eight experiments. Capture cost, candidate validity, API failure, output artifacts, and simulation-vs-measurement labels.
7. **Review and feedback.** Inspect generated recipes and result rows; compare predictions and virtual oracle separately; use human review to approve any candidate for real synthesis. Add only measured results as experimental observations with protocol, replicate, uncertainty and provenance. Refit/retrain only when separately authorized. Recalibrate uncertainty and domain-distance rules, version changes, and require approval for thresholds/weights before the next cycle.
